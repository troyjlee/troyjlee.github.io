Randomised Algorithms

A Motivating Example

Say that we have a vector of size $1{,}000{,}000$ where each entry is zero or one.

We are promised that at least $500{,}000$ entries are one.

The goal is to output the index of an entry that is one.

Scanning from the left works… but in the worst case reads $500{,}001$ entries.

Using Randomness

A randomised algorithm is allowed to flip coins and use the outcomes to decide on its next action.

Different runs of a randomised algorithm on an input can produce different outputs.

We don't require a randomised algorithm to always output the right answer, but instead that it outputs the right answer at least $2/3$ of the time.

The exact fraction doesn't matter too much — we will see how to boost it.

A Randomised Solution

How could we use coin flips to find a one in the input?

Choose a random entry: since at least half the entries are one, the probability it is a one is at least $1/2$.

What is the chance we don't see a one after looking at $2$ random entries? This is like the chance of not seeing heads after flipping a coin twice.

HH HT TH TT

Of the four outcomes only one has no head: the chance of failure is $1/4$.

Driving Down the Error

Similarly, the chance of not seeing a head after $3$ coin flips is $1/8$ — the only "bad" outcome is TTT.

By randomly looking at $t$ entries we reduce the failure probability to $1/2^t$.

Contrast Any deterministic algorithm must read $n/2 + 1$ entries to always succeed. The randomised algorithm reads $30$ entries and fails with probability $2^{-30}$.

Repeat Until Success

Notice that when we query an entry we can see whether it is a one: success is recognisable.

So there is no need to fix a budget in advance — keep querying random entries until we find a one.

This algorithm is never wrong. What varies from run to run is how long it takes.

Each query finds a one with probability at least $1/2$. We will see that the expected number of queries to see a one is 2.

Las Vegas Algorithms

Definition A randomised algorithm is Las Vegas if it always outputs the correct answer, and its running time is a random variable that we bound in expectation.

No matter what the random coins, the answer is right; depending on the random coins it may take longer or shorter to get there.

There is no worst-case bound here: an unlucky run can query for a long time. It halts with probability $1$, and what we control is the expected number of queries.

A More General Setting

Now say the input is an array of $n$ integers.

We want to find the minimum value of the array, and we are guaranteed the minimum value appears at least $d$ times.

Unlike the previous problem, we don't know when we have succeeded — we can't recognise the minimum when we see it.

So repeating until success is not an option: we must fix the number of queries in advance and live with the chance of a wrong answer.

A Generic Randomised Algorithm

Randomly query $T$ entries and return the smallest value amongst them.

It only fails if the minimum value is not amongst the entries queried.

How large should $T$ be to ensure this happens only with small probability?

Monte Carlo Algorithms

Definition A randomised algorithm is Monte Carlo if, on every input, it halts within a worst-case time bound and outputs the correct answer with probability at least $2/3$.

No matter what the random coins, the algorithm will halt within a specified time; depending on the random coins it may get the right answer or not.

Karger's algorithm will be exactly of this kind.

Basic Probability

Coin Flips

Let $p = d/n$. When we randomly choose an entry, the probability it is the minimum value is at least $p$.

If we have a coin that lands heads with probability $p$, how many times do we have to flip it to see a heads with probability at least $9/10$?

Fact By independence of the flips, if we toss the coin $t$ times the probability we do not see a head is $(1-p)^t$.

A Useful Inequality

Fact $1 + x \le e^x$ for any real $x$.

Here $e = 2.718\ldots$ is Euler's constant, $$e = \lim_{n\to\infty}\left(1 + \frac{1}{n}\right)^n.$$

The line $1+x$ is tangent to $e^x$ at $x=0$ and the curve is convex — that is the whole proof.

Applying the Inequality

Taking $x = -p$ gives $1 - p \le e^{-p}$, and so $$(1-p)^t \le e^{-pt}.$$

If we take $t = 1/p$ flips, the failure probability is at most $$\frac{1}{e} \le 0.368.$$

Taking $t = \lceil \ln(10)\rceil/p \le 3/p$ flips pushes the failure probability below $1/10$.

Amplification, Pictured

Write $x = 1/p$. With $t = 1/p$ flips the failure probability is $(1-p)^{1/p} = (1 - \tfrac1x)^{x}$.

With $t = 3/p$ flips it is $(1 - \tfrac1x)^{3x}$.

The curves climb to $1/e$ and $1/e^3$ and never cross them: $(1-p)^t \le e^{-pt}$ for every $p$.

Tripling the flips cubes the failure probability.

Back to Finding the Minimum

An array of $n$ integers whose minimum appears at least $d$ times; output the minimum.

Each random query lands on the minimum with probability $p \ge d/n$.

Conclusion Query $3n/d$ random entries and return the smallest. This is wrong with probability at most $1/10$.

This is a Monte Carlo algorithm: a fixed budget of queries, and a small chance of a wrong answer.

Amplification

The argument is general, as long as a correct answer can be picked out of a batch of runs whenever one is present — here, the smallest value returned.

Fact If each run succeeds with probability at least $p$, then $t \ge 3/p$ independent runs contain a successful one with probability at least $9/10$.

Proof: all $t$ runs fail with probability at most $(1-p)^{t} \le e^{-pt} \le e^{-3} \lt 1/10$.

We will use this twice more today, for Karger's algorithm and its refinement.

Back to Las Vegas

So far we have fixed the number of queries $t$ in advance and bounded the chance of failure by $(1-p)^t$.

Now let's return to the Las Vegas algorithm for finding a one: query random entries until we see a one.

This algorithm never fails. What is random is the number of queries it makes — and we want to bound this on average.

In coin language: a coin lands heads with probability $p$. How many flips until the first heads, on average? Making "on average" precise is the job of expectation.

Expectation

Let us look at the expected number of times we have to flip the coin before we see heads. Let $X$ be a variable representing the number of flips until the first heads.

Definition The expectation of $X$ is a weighted average: $$\E[X] = 1\cdot \Pr[X=1] + 2\cdot \Pr[X=2] + \cdots$$

The Geometric Distribution

In our case of a coin that is heads with probability $p$ we have $$\Pr[X = i] = (1-p)^{i-1}p.$$

So $$\E[X] = 1\cdot p + 2\cdot(1-p)p + 3\cdot(1-p)^2p + \cdots$$

This is tricky, as it is not a geometric series…

Geometric Series

Let's start with an easier case, the geometric series $$p + (1-p)p + (1-p)^2p + (1-p)^3p + \cdots$$

Observation The $i$th term is exactly $\Pr[X = i]$. As the sum of probabilities of disjoint events that cover all outcomes, this series is $1$.

Shift and Subtract

Call the sum $S$, and multiply it by $(1-p)$: every term slides one place to the right.

$$\begin{alignedat}{5} S &{}= 1\cdot p && {}+ 2\cdot (1-p)p && {}+ 3\cdot (1-p)^2p && {}+ \cdots\\ (1-p)\,S &{}= && \phantom{{}+{}} 1\cdot (1-p)p && {}+ 2\cdot (1-p)^2p && {}+ \cdots \end{alignedat}$$

Subtract column by column: each coefficient drops by one.

$$S - (1-p)\,S = p + (1-p)p + (1-p)^2p + \cdots = 1$$

The right-hand side is the geometric series from the previous slide.

Final Expectation

The left-hand side is $S - (1-p)S = p\,S$, so $$p\,S = 1.$$

Fact The expected number of coin flips before we see heads is $\E[X] = S = 1/p$.

Two ingredients only: shifting the sum by one term costs a factor of $(1-p)$, and the leftover is the series we already know.

Back to the First Example

A vector of $1{,}000{,}000$ entries, at least half of them one; output the index of a one.

Each random query lands on a one with probability $p \ge 1/2$.

Conclusion The Las Vegas algorithm — query until we see a one — is always correct and needs $\E[X] = 1/p \le 2$ queries on average.

Compare: any deterministic algorithm must read $500{,}001$ entries to be sure of finding a one.

Putting It Together

Two things to carry forward:

  • independent repetitions drive the failure probability down as $(1-p)^t \le e^{-pt}$ — this one returns for Karger's algorithm,
  • the expected number of trials until the first success is $1/p$.

Minimum Cut and Edge Contraction

Cuts

Say that we are given an undirected, unweighted graph $G$ that is connected.

Definition For every subset of vertices $S$ there is an associated cut: the set of edges with exactly one endpoint in $S$. We denote this set of edges by $\operatorname{cut}(S)$.

Note that $S$ and the complement of $S$ define the same cut.

Minimum Cut

The cut defined by the empty set is not interesting and we ignore it.

When the graph has $n$ vertices there are $2^{n-1} - 1$ interesting cuts: each of the $2^n$ subsets defines a cut, but $S$ and its complement coincide, and we drop $S = \emptyset$.

Minimum Cut

Problem The minimum cut problem is to determine the smallest size of one of these cuts: $$\operatorname{mincut}(G) = \min_{\substack{S\\ 0 \lt |S| \le n/2}} |\operatorname{cut}(S)|$$

Orientation

The degree of a vertex is the number of edges incident to it.

The cut of a single vertex $\{v\}$ is called a star cut; its size is the degree of $v$. So the size of a minimum cut is at most the minimum degree of a vertex.

When there are $n$ vertices, the degree of a vertex is at most $n-1$ — so $\operatorname{mincut}(G) \le n - 1$.

Brute-Force Algorithm

The brute-force algorithm would iterate over every cut and compute its size — time exponential in the number of vertices.

In fact, when the graph has $m$ edges and $n$ vertices there is a randomised algorithm that computes the minimum cut in time $O(m\log^2 n)$ [Gawrychowski, Mozes, Weimann, 2019].

Today A simple randomised algorithm due to Karger that works in time $O(n^2 m\log n)$.

Edge Contraction

The key primitive in Karger's algorithm is edge contraction: delete the edge, merge its endpoints into one new "super-vertex", and keep all outgoing edges with multiplicity.

The result can be a multigraph, i.e. have more than one edge between two vertices. We label the super-vertex with the union of the labels of the original endpoints.

Cuts and Edge Contraction

Any subset $S$ containing both endpoints of the contracted edge maps to a subset $S'$ of the new graph with $|\operatorname{cut}(S)| = |\operatorname{cut}(S')|$ — and every $S'$ in the contracted graph arises this way.

Key Fact Edge contraction cannot decrease the size of a minimum cut.

Sequence of Contractions

The cut defined by $S = \{0,1,2,3\}$ has size 5 (the red edges). Watch this cut as we do a sequence of edge contractions.

Contract the Edge $\{0, 2\}$

Parallel edges appear inside $S$. The cut defined by $\{\{0,2\},1,3\}$ still has size 5.

Contract the Edge $\{4, 5\}$

Contractions on the other side of the cut are harmless too: the cut defined by $\{\{0,2\},1,3\}$ still has size 5.

Contract the Edge $\{\{4,5\}, 6\}$

The cut defined by $\{\{0,2\},1,3\}$ still has size 5.

Takeaway The cut associated with $S$ keeps its size as long as we never contract an edge of the cut itself — an edge $\{i,j\}$ with $i \in S$ and $j \notin S$.

Karger's Algorithm

Karger's Algorithm

KargerMinCut(G):
    while G has more than 2 vertices:
        choose an edge {u, v} uniformly at random
            # among the remaining multi-edges
        contract {u, v}
    return the number of edges between the two remaining vertices

The two remaining super-vertices define a cut of the original graph; the parallel edges between them are exactly the edges of that cut.

Karger's Algorithm

If we never choose an edge in some fixed minimum cut, the algorithm returns exactly that minimum cut.

Intuition A minimum cut is small, so a random edge is unlikely to come from it.

Success Probability: Setup

Say the graph $G$ has $n$ vertices and the size of a minimum cut is $k$. Fix a particular minimum cut $\operatorname{cut}(S)$.

Every vertex has degree at least $k$ — otherwise its star cut would beat the minimum cut.

Fact Summing the degrees, $G$ has at least $nk/2$ edges.

Step 1: The First Contraction

The first contraction is bad if the chosen edge lies in $\operatorname{cut}(S)$.

Our cut has $k$ edges out of at least $nk/2$ in total, so the probability the random edge is one of ours is at most $$\frac{k}{nk/2} = \frac{2}{n}.$$

So the first contraction misses our cut with probability at least $1 - \frac{2}{n} = \frac{n-2}{n}$.

Step 2: And the Next One

Suppose we survived the first contraction. The contracted graph has $n-1$ vertices and still has min cut size at least $k$ (contraction cannot decrease the mincut value), so it has at least $k(n-1)/2$ edges.

The probability the second contraction also misses our cut is at least $$1 - \frac{2k}{k(n-1)} = 1 - \frac{2}{n-1} = \frac{n-3}{n-1}.$$

Step 2: And the Next One

So the probability we are still good after two contractions is at least $$\frac{n-2}{n}\cdot\frac{n-3}{n-1}.$$

Step 3: In General

After the second contraction there are at least $k(n-2)/2$ edges, so the third contraction misses with probability at least $1 - \frac{2}{n-2} = \frac{n-4}{n-2}$, giving $$\frac{n-2}{n}\cdot\frac{n-3}{n-1}\cdot\frac{n-4}{n-2}$$ after three contractions.

Step 3: In General

In general, at the $i$th contraction there are $n-i+1$ vertices left, and the success probability of that step is at least $$\frac{n-i-1}{n-i+1}.$$

The Telescoping Product

We do $n-2$ contractions to reach 2 vertices. The success probability is at least

$$\frac{n-2}{n}\cdot\frac{n-3}{n-1}\cdot\frac{n-4}{n-2}\cdot\frac{n-5}{n-3} \cdots\frac{3}{5}\cdot\frac{2}{4}\cdot\frac{1}{3} \;=\; \frac{2}{n(n-1)}.$$

Every numerator cancels a denominator two steps later — only $n$ and $n-1$ survive below, and $2\cdot 1$ above.

Lemma A single run of Karger's algorithm outputs a fixed minimum cut with probability at least $\dfrac{2}{n(n-1)}$.

Amplification by Repetition

Run the algorithm $t$ times independently and return the minimum cut value found. We fail only if every run fails; by independence,

$$\Pr[\text{all } t \text{ runs fail}] \le \left(1 - \frac{2}{n(n-1)}\right)^{t} \le e^{-2t/(n(n-1))}$$

using our inequality $1 + x \le e^x$.

Amplification by Repetition

Theorem With $t = 3n(n-1)/2$ repetitions, the failure probability is at most $e^{-3} \lt 1/10$: we find a minimum cut with probability at least $9/10$.

This is the amplification fact with $p = 2/(n(n-1))$: $3/p$ repetitions.

Implementation of One Run

Rather than randomly choosing a remaining edge at each step, it is easier to take an alternative, but equivalent, viewpoint.

We first randomly order the edges; this ordering determines the order in which we contract them. Assign the $i$th edge in the ordering weight $i$ and run Kruskal's MST algorithm (Week 5!).

Implementation of One Run

The partition of vertices into connected components at any stage represents the super-vertices of the contracted graph.

Before the last edge is added in Kruskal's algorithm there are just two connected components — the edges between these sets are the proposed mincut.

Running Time

Via Kruskal with union–find, one round of Karger's algorithm runs in time $O(m\log n)$ when there are $m$ edges.

Total With $O(n^2)$ repetitions, the overall running time is $O(n^2\, m\log n)$.

Note that during the algorithm we work with a multigraph. We could also start from a multigraph — the algorithm works on weighted graphs with non-negative integer weights.

Cool Consequence

We fixed a minimum cut and argued that the probability this cut is preserved by the algorithm is at least $\frac{2}{n(n-1)}$. This holds for any minimum cut.

Different minimum cuts being returned are disjoint events, and the probabilities of disjoint events sum to at most $1$.

Corollary The number of minimum cuts in a graph is at most $\dfrac{n(n-1)}{2}$.

Remarkably, this bound is exactly tight!

Tight Example: the Cycle Graph

In a cycle the size of a minimum cut is $2$.

Removing any two edges disconnects the graph, and there are $\binom{n}{2} = \frac{n(n-1)}{2}$ ways to remove two edges.

So the cycle graph $C_n$ has exactly $\frac{n(n-1)}{2}$ minimum cuts — matching the bound.

The Karger–Stein Algorithm

High Risk Contractions

Look again at the telescoping product, our lower bound on the probability that no contraction ever picks an edge of a fixed minimum cut: $$\frac{n-2}{n}\cdot\frac{n-3}{n-1}\cdot\frac{n-4}{n-2}\cdots\frac{2}{4}\cdot\frac{1}{3}.$$

The first factor is $1 - \frac{2}{n}$: the first contraction is almost never bad.

The last factor is $\frac{1}{3}$: the final contraction is bad one time in three.

High Risk Contractions

Observation The risk is concentrated in the last few contractions.

Yet repetition treats every contraction alike: it restarts from scratch $\Theta(n^2)$ times, redoing the safe early part every time.

Stopping Early

What if we stop once $t$ vertices remain, after $n - t$ contractions?

The same product, cut short, bounds the probability that our cut survives: $$\frac{n-2}{n}\cdot\frac{n-3}{n-1}\cdots\frac{t-1}{t+1} \;=\; \frac{t(t-1)}{n(n-1)}.$$

Everything still cancels two steps later; now $t$ and $t-1$ survive on top. Sanity check: $t = 2$ gives back $\frac{2}{n(n-1)}$.

Early Contractions Are Safe

How far can we contract while keeping the cut with probability at least $1/2$?

Take $t = \lceil n/\sqrt2\rceil + 1$. Both $t$ and $t-1$ are at least $n/\sqrt2$, so

$$\frac{t(t-1)}{n(n-1)} \;\ge\; \frac{n^2/2}{n(n-1)} \;\ge\; \frac12.$$
Lemma Contracting down to $t = \lceil n/\sqrt2\rceil + 1$ vertices keeps a fixed minimum cut with probability at least $1/2$.

Recycling the Safe Part

For $n = 1000$: the first $291$ of the $998$ contractions keep the cut with probability at least $\frac12$. The danger lives in the remaining $707$.

Better: contract down to $t$ vertices once, then find a minimum cut of the smaller graph — recursively.

Recycling the Safe Part

Each level of recursion shrinks $n$ by a factor of $\sqrt2$, so there are about $d = 2\log_2 n$ levels.

Problem Each level keeps the cut with probability only $\frac12$, and the losses compound: $\left(\frac12\right)^{2\log_2 n} = \frac{1}{n^2}$. We are back where we started.

No surprise: contracting all the way down in stages is still just one run of Karger's algorithm.

Two Tries at Every Level

A factor of $\frac12$ per level is a coin flip per level. Where we risk a coin flip, give ourselves a second one.

At each level, contract to $t$ vertices twice, independently, and recurse on both smaller graphs. Return the smaller of the two answers.

Why not three or four tries? We will see that the time budget allows exactly two.

The Karger–Stein Algorithm

KargerStein(G):
    n = number of vertices of G
    if n ≤ 6: return a minimum cut of G by brute force
    t = ⌈n/√2⌉ + 1
    G1 = Contract(G, t)   # contract random edges until t vertices remain
    G2 = Contract(G, t)   # independently of G1
    return min(KargerStein(G1), KargerStein(G2))

The recursion tree is a full binary tree of depth $d \approx 2\log_2 n$. [Karger-Stein, 1996]

Why Not Kruskal Again?

One run of Karger contracted via Kruskal, in $O(m\log n)$ time.

Contraction only deletes self-loops; every other edge survives as a parallel edge. A subproblem on $t$ vertices can still hold all $m$ edges, so Kruskal still costs $\Omega(m)$.

The recursion tree has $2^d = n^2$ leaves. Paying $m$ per call gives $\Omega(m\,n^2)$: no better than repeating Karger $n^2$ times.

Need A representation whose cost shrinks with the number of vertices $t$, not with $m$.

Running Time

Store the multigraph as an $n \times n$ table of edge multiplicities: size $n^2$ no matter how many parallel edges there are.

Contracting an edge merges two rows and two columns: $O(n)$ time.

Choosing a random edge also takes $O(n)$ time: pick an endpoint $u$ with probability proportional to its degree, then a neighbour $v$ with probability proportional to the multiplicity of $\{u, v\}$.

Running Time

Fact $\textsf{Contract}(G, t)$ does fewer than $n$ contractions of $O(n)$ time each, so it runs in $O(n^2)$ time.

Each call does two contractions and two recursive calls on graphs with $t \approx n/\sqrt2$ vertices: $$T(n) \;\le\; 2\,T\!\left(n/\sqrt2\right) + O(n^2).$$

The Recursion Tree

Level $i$ has $2^i$ subproblems on $n/2^{i/2}$ vertices, each costing $O(n^2/2^i)$: every level costs $O(n^2)$, and there are $d \approx 2\log_2 n$ levels.

Theorem One run of Karger–Stein takes $O(n^2\log n)$ time.

Why Exactly Two?

Shrinking to $n/\sqrt2$ was forced by wanting survival probability $\frac12$.

Two branches of size $n/\sqrt2$ cost $2\cdot\frac{n^2}{2} = n^2$: exactly the cost of the level above.

With three branches the levels would grow geometrically, and the time would be $n^{\log_{\sqrt2} 3} \approx n^{3.17}$.

Balance Two is the most branching that keeps the cost per level flat.

Success Probability

Let $p_k$ be a lower bound on the probability that a call at height $k$ of the recursion tree finds a fixed minimum cut of its input graph.

Leaves (height $0$) use brute force: $p_0 = 1$.

To bound $p_{k+1}$, fix a minimum cut $C$ of the input graph of a call at height $k+1$, and ask when one of its two branches finds $C$.

Height 1

The whole tree when $n = 7$: contract $7 \to 6$ vertices twice, then brute force. A branch finds $C$ if its contraction keeps $C$: probability at least $\frac12$.

Both branches fail with probability at most $\left(\frac12\right)^2 = \frac14$.

So $p_1 \ge 1 - \left(1 - \frac{p_0}{2}\right)^2 = 1 - \frac14 = \frac34$, against $\frac12$ with one branch.

Height 2

Now $n = 8$: contract $8 \to 7$ twice. Each child is the height-1 tree: success probability at least $\frac34$.

A branch finds $C$ if its contraction keeps $C$ and its subtree then finds $C$: at least $\frac12\cdot\frac34 = \frac38$. Both fail with probability at most $\left(\frac58\right)^2 = \frac{25}{64}$.

So $p_2 \ge 1 - \left(1 - \frac{p_1}{2}\right)^2 = \frac{39}{64} \approx 0.61$, against $\frac14$ with one branch per level.

Same rule at every level: a branch succeeds with probability $\frac{p_k}{2}$, and both must fail.

One branch halves at every level. Two branches sink slowly — the dashed curve is $1/(k+1)$.

One Branch

For a branch to find $C$, two things must happen.

Event 1 $\textsf{Contract}$ at height $k+1$ never chooses an edge of $C$. By the Lemma this has probability at least $\frac12$. Then $C$ is still a minimum cut of the contracted graph.
Event 2 $C$ also survives every later round: the recursive call at height $k$ finds $C$. By the definition of $p_k$ this has probability at least $p_k$.

Success Probability

The recursive call picks fresh random edges, independent of the contraction, so both events happen with probability at least $\frac12 \cdot p_k$.

So one branch fails with probability at most $1 - \frac{p_k}{2}$.

The call fails only if both branches fail, and the two branches are independent: $$p_{k+1} \;\ge\; 1 - \left(1 - \frac{p_k}{2}\right)^2 \;=\; p_k - \frac{p_k^2}{4}.$$

Harmonic, Not Geometric

One branch: $p \mapsto p/2$. Halving at every level leaves $2^{-d} = 1/n^2$ at the root.

Two branches: $p \mapsto p - p^2/4$. For small $p$ the loss $p^2/4$ is much smaller than $p$: the curve hugs the line $y = p$.

Claim $p_k \ge \dfrac{1}{k+1}$ for every $k \ge 0$.

Harmonic, Not Geometric

Induction on $k$; the base case is $p_0 = 1$. The function $x - \frac{x^2}{4}$ is increasing for $x \le 2$, so $p_k \ge \frac{1}{k+1}$ gives

$$\begin{aligned} p_{k+1} &\;\ge\; p_k - \frac{p_k^2}{4} \\ &\;\ge\; \frac{1}{k+1} - \frac{1}{4(k+1)^2} \\ &\;\ge\; \frac{1}{k+1} - \frac{1}{(k+1)(k+2)} \;=\; \frac{1}{k+2}. \end{aligned}$$

The last step uses $4(k+1) \ge k+2$.

Putting It Together

The root is at height $d \approx 2\log_2 n$.

Theorem One run of Karger–Stein finds a fixed minimum cut with probability at least $\frac{1}{d+1} = \Omega(1/\log n)$, in time $O(n^2\log n)$.

Amplify as before: $3(d+1) = O(\log n)$ independent runs fail with probability at most $e^{-3} \lt \frac{1}{10}$.

Total A minimum cut with probability at least $\frac{9}{10}$ in $O(n^2\log^2 n)$ time.

Notes

Karger's algorithm dates from 1993 and the Karger–Stein refinement from 1996. A different idea, packing spanning trees, gave $O(m\log^3 n)$ time [Karger, 2000].

The current best randomised algorithm runs in time $O(m\log^2 n)$ [Gawrychowski, Mozes, Weimann, 2019], and near-linear time deterministic algorithms are also known.
